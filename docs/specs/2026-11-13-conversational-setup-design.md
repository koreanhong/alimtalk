# 설계: 대화형 알림톡 템플릿 세팅

- 작성일: 2026-11-13
- 상태: 승인됨 (2026-11-13, [제안] 항목 포함). 5.1 화면 배치는 같은 날 사용자 결정으로 왼쪽 아래 챗봇으로 변경
- 선행 설계: `docs/specs/2026-11-12-nl-alimtalk-template-design.md` (자연어 한 번에 채우기, 구현 완료)
- 표기: **[사용자 결정]** 사용자가 정한 것 / **[제안]** 설계자가 정한 것(검토 중 바꿀 수 있음)

## 1. 의도와 배경

지금은 자연어 한 문장으로 폼을 한 번에 채운다. 이를 **대화하면서 세팅하는 방식**으로 바꾼다.

이유 **[사용자 결정]**
- 무엇을 입력해야 할지 모르는 사용자가 있다.
- 직접 세팅하면 읽기 쉽고 깔끔한 메시지를 만들기 어려울 때가 있다.

대화형은 사용자를 이끄는 **안내자**이자 문구를 잘 다듬는 **작성자** 역할을 한다. 질문마다 **선택지 버튼 클릭**과 **직접 입력** 둘 다로 답할 수 있다.

## 2. 목표 / 비목표 / 반목표

### 목표
- **새로 만들기** **[사용자 결정]**: 빈 상태에서 대화로 템플릿을 만든다. 정보가 부족하면 질문과 선택지를 내고, 충분하면 바로 작성한다.
- **다듬기** **[사용자 결정]**: 사용자가 폼에 직접 쓴 내용을 대화로 다듬는다. 고친 결과를 먼저 보여 주고 [적용]/[취소]를 고르게 한다.
- 질문마다 선택지 버튼 + 직접 입력을 함께 제공한다 **[사용자 결정]**.
- 결과는 지금처럼 폼과 미리보기에 채우고, 사용자는 언제든 폼을 직접 고칠 수 있다.

### 비목표
- 자동 세팅 범위 확장 **[사용자 결정: 지금 범위 유지]**: 메시지 유형 기본형·부가정보형, 강조 유형 선택 안 함·강조 표기형만. 채널추가형·복합형·이미지형·아이템리스트형·버튼은 지금처럼 직접 설정한다.
- 대화 기록의 장기 저장(새로고침하면 새 대화) **[제안]**
- 실제 발송, 브랜드 메시지

### 반목표 (동작해도 실패로 보는 것)
- 사용자가 확인하지 않은 다듬기 결과가 폼에 바로 덮어써지는 것
- 직접 설정한 버튼·이미지·아이템리스트가 다듬기 때문에 사라지는 것
- 질문만 계속 이어지고 템플릿이 완성되지 않는 것(질문 횟수 상한 필요)
- 카카오 규칙 위반 결과를 표시 없이 채우는 것(기존 규칙 점검 유지)

## 3. 제약
- 기존 구조 재사용: Spring Boot 서버, Claude API(`claude-opus-5-5`, effort medium, 구조화 출력, 시스템 프롬프트 캐싱), 규칙 파일·규칙 점검기·재생성 루프, 사용량 CSV 기록, 화면 `static/index.html`.
- 카카오 규칙과 생성 지침(`rules/alimtalk-review-guide.md`)은 그대로 따른다.
- 호출당 비용(약 1센트, 캐시 적용 시 추정)과 2~6초 지연이 질문마다 생긴다(2026-11-13 실측 기준).

## 4. 구현 방식 검토 (Approaches)

| 방식 | 내용 | 장단점 |
|---|---|---|
| **1. Claude 주도** (선택) | 시작 버튼만 고정. 이후 질문·선택지·작성 여부를 Claude가 판단 | 어떤 답이든 자연스럽게 이어지고, 정보가 충분하면 바로 작성. 질문 목록 관리 불필요. 대신 턴마다 비용·지연이 있고 질문이 매번 조금 다를 수 있음 |
| 2. 정해진 단계(마법사) | 질문 순서·선택지를 미리 정의, Claude는 마지막 작성·다듬기만 | 빠르고 저렴, 예측 가능. 대신 카테고리별 목록 관리 필요, 자유 입력에 약하고 정보가 충분해도 단계를 다 거침 |
| (제외) 버튼 없는 자유 대화 | — | "클릭으로도 선택" 요청과 맞지 않음 |

**[사용자 결정]** 방식 1. 이유: 무엇을 입력할지 모르는 사용자에게 시작 버튼이 길잡이가 되고, 이후 질문은 상황에 맞게 이어진다.

## 5. 동작

### 5.1 화면 흐름 **[사용자 결정, 2026-11-13 변경: 왼쪽 아래 챗봇]**
목업: `build/mockups/chatbot-F.png`(닫힌 상태), `chatbot-E.png`(열린 상태) — git 제외 폴더.

- **닫힌 상태**: 화면 왼쪽 아래에 떠 있는 동그란 💬 버튼만 둔다(스크롤해도 고정). 기존 폼 위 "자연어로 작성" 칸은 없앤다.
- **열린 상태**: 버튼을 누르면 왼쪽 아래에 챗봇 창(가로 약 380 × 세로 약 560)이 열린다. 오른쪽 휴대폰 미리보기는 가리지 않는다.
- 창 머리: 제목 "알림톡 자동완성", [새 대화], [−] 접기, [×] 닫기. **접기·닫기는 창만 숨기고 대화는 유지**한다(다시 열면 이어서). [새 대화]는 대화를 지우고 시작 선택지부터 다시 보여 준다. 새로고침하면 대화는 사라진다.
- 첫 인사: "안녕하세요! 어떤 알림톡 메시지를 만들까요?" + 시작 선택지(아래) + 작은 글씨 안내 "자동 작성은 메시지 유형 기본형·부가정보형, 강조 유형 선택 안 함·강조 표기형만 채웁니다. 채널추가형·복합형, 이미지형·아이템리스트형 강조, 버튼은 폼에서 직접 설정해 주세요."

```
닫힌 상태                     열린 상태(왼쪽 아래)
                              ┌ 알림톡 자동완성  [새 대화][−][×] ┐
                              │ 어떤 알림톡 메시지를 만들까요?     │
                              │ [주문 완료][주문 취소][배송 시작]  │ ← 시작 선택지(고정, Claude 호출 없음)
                              │ [예약 확정][회원가입][인증번호]    │
                              │ [지금 폼 다듬기]                  │
                              │ (범위 안내, 작은 글씨)             │
                              │              나: 생성해줘          │
                              │ 어떤 유형의 메시지인가요?          │
                              │ [배송 안내][인증번호][주문 완료]…   │ ← Claude가 만든 선택지
 (💬)                         │ [입력...                ][보내기] │
                              └────────────────────────────────┘
```
- 시작 선택지를 누르면 그 이름이 사용자 발화로 들어간다(예: "배송 시작 안내 메시지").
- 선택지 버튼은 **가장 최근 응답의 것만** 누를 수 있다(이전 것은 회색 비활성). 누르면 버튼 문구가 사용자 발화가 된다.
- 직접 입력은 항상 가능하다(Enter로 보내기). 첫 발화로 충분한 문장을 쓰면 질문 없이 바로 작성된다.
- [지금 폼 다듬기]는 템플릿 내용(본문)이 비어 있지 않을 때만 누를 수 있다.
- 요청 처리 중에는 창 안에 "작성 중…"을 표시하고 입력·버튼을 막는다.

### 5.1.1 새로 만들기 / 다듬기 판단 **[사용자 결정: Claude가 판단]**
- 화면은 **항상 현재 폼의 텍스트 항목을 함께 보낸다**(화면은 예시 템플릿이 채워진 상태로 열리므로 폼은 대부분 비어 있지 않다).
- Claude가 발화를 보고 판단한다: "배송 안내 만들어줘"처럼 새 메시지를 요청하면 **새로 만들기**, "더 정중하게"처럼 지금 내용을 고치라고 하면 **다듬기**.
- [지금 폼 다듬기] 버튼은 다듬기 요청 문구("지금 폼을 다듬어줘")를 발화로 보낸다. 시작 버튼은 새로 만들기 문구("배송 시작 안내 메시지")를 보낸다.
- 응답에 판단 결과(`mode`: NEW/POLISH)를 담는다. 화면은 NEW면 5.2, POLISH면 5.3 방식으로 처리한다.
- 덮어쓰기를 취소했거나 규칙 위반으로 아직 폼에 넣지 않은 초안이 있을 때의 다음 발화도 같은 규칙(현재 폼 + Claude 판단)을 따른다. 넣지 않은 초안은 대화 기록(assistant 발화의 요약)으로만 남는다 **[제안]**.

### 5.2 새로 만들기
- 대화 결과로 초안이 오면 **기존 적용 흐름**(`applyDraft`)을 그대로 쓴다: 폼이 수정된 상태면 덮어쓰기 확인 창, 버튼·아이템리스트·이미지 비움, 경고 표시, 규칙 위반이면 [그래도 폼에 채우기]/[다시 생성].
- 작성 후에도 대화를 이어 수정할 수 있다(예: "더 짧게"). 이때는 방금 채운 폼이 "현재 폼"이 되고, Claude가 다듬기로 판단한다.

### 5.3 다듬기
- [지금 폼 다듬기] 또는 폼에 내용이 있는 상태에서 다듬기 요청 시, **현재 폼의 텍스트 항목**(카테고리, 이름, 코드, 메시지 유형, 강조 유형, 강조 제목·보조 문구, 본문, 부가정보, 보안 여부, 변수 예시값)을 함께 보낸다.
- Claude가 "어떻게 다듬을까요? [더 짧게] [항목별로 정리] [더 정중하게]"처럼 묻거나, 요청이 분명하면 바로 고친다.
- 고친 결과는 **폼에 바로 넣지 않고** 대화 카드에 변경 요약과 함께 보여 준다. [적용]을 누르면 위 텍스트 항목만 바꾸고 **버튼·이미지·아이템리스트·채널·채널추가형 설정은 그대로 둔다**. [취소]하면 아무것도 바꾸지 않는다.
- 다듬기 결과도 규칙 점검·재생성을 거친다. 위반이 남으면 새로 만들기와 같은 방식으로 위반 내용을 보여 주고 [그래도 적용]/[다시 다듬기]를 고르게 한다 **[제안]**.
- 재생성은 Claude가 고칠 수 있는 항목(Claude에 보낸 텍스트 항목)의 위반만 대상으로 한다. Claude에 보내지 않는 항목(아이템리스트 등)에서 생긴 위반은 재생성하지 않고 표시만 한다 **[제안]**. 사용자가 처음부터 위반 상태로 쓴 내용도 다듬기 결과에서 남아 있으면 위반으로 표시한다.
- 폼의 메시지 유형이 채널추가형·복합형이거나 강조 유형이 이미지형·아이템리스트형이면 **[제안]** 그 유형은 유지하고 텍스트(본문·부가정보 등)만 다듬는다. 이를 위해 규칙 점검은 다듬기에서 "유형 허용값 검사"를 폼의 원래 유형 기준으로 통과시킨다(세부는 빌더 재량, 6.4 참고).

### 5.4 질문 횟수 상한 **[제안]**
- Claude가 연속으로 질문만 3번 하면, 4번째 응답은 반드시 작성하도록 서버가 지시(시스템 메시지)를 추가한다. 대화 전체는 최대 20개 발화(사용자+시스템)까지만 받는다.

## 6. API·응답 형식

### 6.1 `POST /api/templates/chat` (신규) **[제안]**
요청
```json
{
  "messages": [
    {"role": "user", "text": "배송 시작 안내 메시지"},
    {"role": "assistant", "text": "배송 안내에 무엇을 넣을까요?"},
    {"role": "user", "text": "택배사·송장번호"}
  ],
  "channel": "@mystore",
  "form": { "...": "현재 폼 텍스트 항목(TemplateDraft 형식). 항상 보냄(비어 있으면 빈 값)" }
}
```
- `messages`: 1~20개, 각 `text` 1~500자, 마지막은 `user`. `assistant` 발화는 화면이 서버 응답의 `reply.text`를 그대로 보관해 보낸다.
- 대화 기록은 **화면(브라우저 메모리)에만** 보관한다. 서버는 저장하지 않는다 **[제안]**.

응답 200
```json
{
  "kind": "ASK | DRAFT | REJECTED",
  "mode": "NEW | POLISH (DRAFT일 때)",
  "reply": { "text": "배송 안내에 무엇을 넣을까요?", "choices": ["택배사·송장번호", "배송 예정일", "상품명"] },
  "draft": { },
  "warnings": [],
  "errors": [],
  "attempts": 1
}
```
- `ASK`: 질문. `choices` 0~6개(각 20자 이내). `draft` 없음.
- `DRAFT`: 작성 완료(새로 만들기) 또는 다듬기 결과. `reply.text`는 한 줄 요약(예: "택배사·송장번호를 넣어 배송 시작 안내를 작성했습니다."), `choices`는 후속 제안(예: [고객센터 안내 추가] [이대로 완료]). 규칙 위반이 남으면 `errors`에 담는다(기존 422 대신 200 + errors로 통일 **[제안]**: 대화 흐름에서 오류도 하나의 응답으로 보여 주기 위함).
- `REJECTED`: 광고 요청 등. `reply.text`에 이유와 안내.
- 400(입력 검증), 502/504(Claude 오류·시간 초과)는 기존과 같다.

### 6.2 기존 `POST /api/templates/generate` **[사용자 결정: 남기고 '되묻기'로 통일]**
- 주소·요청·응답 형식은 그대로 남긴다. 화면에서는 더 쓰지 않는다.
- 생성 지침을 하나로 합치므로, 애매한 요청에는 가정 작성(B) 대신 되묻는다(`UNCLEAR` 응답). 구체적인 요청은 지금처럼 바로 작성한다. 관련 기존 테스트는 바뀐 동작에 맞게 수정한다.

### 6.3 Claude 응답 형식 (`LlmOutput` 확장)
- `status`: `OK`(작성) / `ASK`(질문) / `AD_CONTENT`(거절). 기존 `UNCLEAR`는 대화형에서 `ASK`로 대체한다.
- `ASK`일 때 `question`(문장)과 `choices`(문자열 배열, 최대 6)를 채운다.
- 기존 "애매하면 가장 일반적인 경우로 작성 + 가정 표시"(B) 규칙은 **"애매하면 질문"으로 바뀐다**(대화형·기존 API 공통, 6.2). 단, 정보가 충분하면 바로 작성한다.
- 작성(`OK`)일 때 `mode`(NEW/POLISH)를 채운다.
- 다듬기에서는 `draft`에 고친 결과를 담고, `message`에 변경 요약 한 줄을 담는다.

### 6.4 Claude 호출 구성
- 시스템 프롬프트: 기존 생성 지침 + "대화형 규칙"(질문은 짧게, 선택지는 최대 6개 버튼 문구로, 정보가 충분하면 바로 작성, 다듬기 시 의미·변수를 바꾸지 않고 형식만 개선 등). 요청마다 동일하게 유지해 캐시가 깨지지 않게 한다.
- `messages`: 대화 기록을 user/assistant 턴으로 그대로 전달. 현재 폼 내용(발신 채널 포함)은 첫 user 턴 앞쪽에 붙인다(폼은 매 요청 달라질 수 있으므로 시스템 프롬프트가 아니라 메시지에 넣어 캐시를 유지). 매 요청 그 시점의 폼으로 다시 만든다(구현 기준으로 갱신).
- 재생성(규칙 위반 시 최대 2회)·시간 예산(호출 60초, 요청 120초)은 기존과 같다. 재생성 요청은 대화 기록 뒤에 위반 내용을 붙인 user 턴으로 보낸다.
- 다듬기에서 폼의 유형이 자동 세팅 범위 밖(AD/MI/IMAGE/ITEM_LIST)이면, Claude에는 "유형은 바꾸지 말 것"을 지시하고, 서버는 응답의 유형 대신 폼의 원래 유형을 유지한 채 텍스트 항목만 반영한다(빌더 재량으로 구현).

## 7. 사용량 기록
- 대화의 **턴(요청) 1번마다 1줄** 기록한다(기존 CSV 재사용).
- 결과 값에 질문 `ASK`를 추가하고(작성은 기존과 같이 `SUCCESS`/`RULE_VIOLATION`, 거절은 `AD_CONTENT`, 오류는 `ERROR_*` — 구현 기준으로 갱신), 열 끝에 `모드`(NEW/POLISH, 질문·거절이면 빈칸), `대화턴수`(messages 개수)를 추가한다 **[제안]**. 기존 파일의 제목 줄과 열 수가 달라지므로, 열이 바뀌면 새 파일명(`llm-usage-v2.csv`)으로 기록한다 **[제안]**.
- 요청 문장 열에는 마지막 사용자 발화를 기록한다.
