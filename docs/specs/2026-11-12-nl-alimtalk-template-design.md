# 설계: 자연어로 알림톡 템플릿 폼 자동 작성

- 작성일: 2026-11-12
- 상태: 승인됨 (2026-11-12, [제안] 항목 포함 전체 승인)
- 관련 파일: `alimtalk-template.html` (기존 템플릿 등록 화면 시안), `docs/handoff.md`

표기: **[사용자 결정]** 은 사용자가 직접 정한 것, **[제안]** 은 설계자가 정한 것으로 사용자가 검토 중 바꿀 수 있다.

## 1. 의도와 배경

알림톡 템플릿은 카테고리, 메시지 유형, 본문, 변수, 부가정보 등 채울 항목이 많고 카카오 심사 규칙을 지켜야 해서 작성이 번거롭다. 사용자가 "주문 관련 메시지 세팅해줘"처럼 자연어로 요청하면, 카카오 알림톡 규칙에 맞게 템플릿 등록 폼이 자동으로 채워지도록 한다. 사용자는 채워진 폼을 확인·수정만 한다.

- 처음에는 "광고 발송 세팅"까지 원했으나, 알림톡은 정보성 메시지만 허용되므로 **알림톡 + 정보성 템플릿 작성**으로 범위를 좁혔다. **[사용자 결정]**
- 광고성 메시지(브랜드 메시지)와 실제 발송 설정(수신 대상·시점)은 이후 단계 후보다.

## 2. 목표 / 비목표 / 반목표

### 목표
- 자연어 한 문장으로 기존 템플릿 등록 폼의 항목을 자동으로 채운다.
- 채워진 결과는 로컬 규칙 파일 기준으로 자동 점검되고, 위반 시 자동으로 재생성되어 규칙을 지키는 상태로 폼에 들어간다.
- 사용자는 자동으로 채워진 폼을 직접 고칠 수 있고, 미리보기는 기존처럼 즉시 반영된다.

### 비목표 (이번 범위 아님)
- 실제 알림톡 발송, 수신 대상·발송 시점 설정 **[사용자 결정]**
- 브랜드 메시지(친구톡) 등 광고성 메시지 **[사용자 결정]**
- 버튼 자동 생성 **[사용자 결정]** (버튼은 화면에서 수작업으로 설정 — 2026-11-12 변경)
- 검수 기능: 시안의 "검수 요청 데이터 생성" 버튼과 "검증 결과·요청 페이로드" 영역 **[사용자 결정: "검수기능은 빼줘"]**
- 딜러사(발송 대행사) API 연동, 카카오 검수 요청 전송
- 이미지형 강조 자동 생성 **[제안]**
- 자연어로 반복 수정("좀 더 짧게") — 다음 단계 **[제안]**
- 로그인·사용자 관리, DB 저장

### 반목표 (기술적으로 동작해도 실패로 보는 것)
- 생성된 템플릿이 카카오 심사 가이드상 명백히 반려될 내용(광고성 문구, 발송 불가 예시 해당, 변수만으로 된 본문 등)을 담는 것
- API 키가 브라우저, 저장소, 로그에 노출되는 것
- 규칙 위반 결과를 아무 표시 없이 폼에 넣는 것

## 3. 제약

- 알림톡은 정보성 메시지만 허용, 카카오 템플릿 심사는 필수(우리 시스템 밖에서 진행).
- 규칙 출처: 내용 기준은 카카오 비즈니스 알림톡 심사 가이드(https://kakaobusiness.gitbook.io/main/ad/infotalk/audit) **[사용자 결정]**. 이 가이드에는 글자 수 제한이 없으므로 형식 수치는 딜러사 API 문서를 따른다. 딜러사는 미정.
- 규칙은 매번 원문을 가져오지 않고 로컬 파일로 관리한다 **[사용자 결정]**.
- 기술 스택: Java 21, Spring Boot 3.x, Gradle **[사용자 결정]**. LLM은 Claude API(Anthropic 공식 Java SDK), 모델 `claude-opus-5-5` **[사용자 결정]**.
- API 키는 사용자가 개인 Claude Console에서 발급 **[사용자 결정]**. 서버 환경변수 `ANTHROPIC_API_KEY`로만 주입하고 저장소·설정 파일에 넣지 않는다.
- 현재 저장소는 제로베이스(HTML 시안 1개, git 아님).

## 4. 구현 방식 검토 (Approaches)

| 방식 | 내용 | 장단점 |
|---|---|---|
| **A. LLM 생성 + 규칙 점검** (선택) | 자연어 + 규칙(심사 지침, 형식 수치)을 Claude에 전달, 구조화 출력으로 폼 JSON을 받고 Java에서 규칙 점검, 위반 시 재생성 | 자유 문구 생성 요구에 부합. 서버 필요, 호출 비용, 결과가 매번 다름 |
| B. 키워드 매칭 + 사전 템플릿 | "주문/배송/예약" 키워드로 미리 작성한 템플릿을 채움 | 서버·LLM 불필요, 결과 일정. 사실상 자연어 이해가 아니고 준비된 범위 밖 대응 불가 |
| C. LLM 의도 판단 + 사전 템플릿 다듬기 | LLM은 템플릿 선택·소폭 수정만 | 균형적이나 서버는 필요하고 문구 자유도가 낮음 |

사용자는 **A**를 선택했다. "내용도 임의로 설정"이라는 요구를 충족하는 유일한 방식이기 때문이다.

## 5. 전체 구조

```
[브라우저: 기존 HTML(수정) + 자연어 입력창]
        │ POST /api/templates/generate   { "prompt": "...", "channel": "@mystore" }
        ▼
[Spring Boot]
  ├ RuleLoader      : classpath rules/ 로드 (기동 시 1회)
  ├ TemplateGenerator: Claude API 호출 (구조화 출력 → TemplateDraft JSON)
  ├ RuleValidator   : alimtalk-rules.json 기준 점검
  └ 재생성 루프      : 위반 시 위반 목록을 붙여 재요청 (최대 N회)
        ▼ 200 { draft, warnings[] }  또는 422 { reason }
[브라우저: 폼 자동 채움 → 기존 update()로 카운터·미리보기 갱신]
```

- 기존 HTML은 Spring Boot 정적 리소스(`src/main/resources/static/index.html`)로 옮겨 서빙한다. 프론트엔드 프레임워크는 도입하지 않는다. **[제안]**
- 단일 Gradle 모듈. 패키지 루트는 미정이며 빌더가 정한다(예: `com.<org>.alimtalk`).

## 6. 상세

### 6.1 규칙 파일 **[사용자 결정: 로컬 파일 관리 / 제안: 구성]**

`src/main/resources/rules/` (저장소 루트 `rules/`가 아니라 classpath에 둬서 배포물에 포함되게 한다 **[사용자 결정]**. 외부 경로·외부 경로 우선 방식과 비교 후 선택. 규칙 변경 시 재빌드·재배포 필요. 필요해지면 "classpath 기본 + 외부 경로 우선" 방식으로 확장 가능)

1. `alimtalk-rules.json` — 코드 점검용 수치·형식 규칙
   - 메타: `source`(URL 목록), `checkedAt`(확인 날짜), `note`
   - 항목(초기값은 아래 6.1.1)
2. `alimtalk-review-guide.md` — LLM 시스템 프롬프트에 넣을 생성 지침
   - 정보성 메시지 정의, 형식화 가능 원칙, 정보성으로 보는 경우, 발송 불가 예시(심사 가이드 요약)
   - 주문·배송·예약·회원 등 카테고리별 작성 예시(심사 가이드 "발송 가능 예시" 페이지 확인 후 요약)
   - 맨 위에 출처 URL과 확인 날짜

규칙 갱신은 사람이 원문과 비교해 파일을 수정하는 방식이다. 자동 동기화는 하지 않는다.

작성 주체 **[사용자 결정]**: `alimtalk-review-guide.md`는 구현 첫 단계에서 Claude가 카카오 심사 가이드와 발송 가능 예시를 요약해 초안을 만들고, 사용자가 검토·승인한 뒤 다음 구현으로 넘어간다.

#### 6.1.1 초기 규칙 수치 **[제안]**
딜러사가 정해지기 전까지는 확인된 값 중 **더 엄격한 쪽**을 쓴다.

수준: **오류** = 재생성 대상, 끝까지 남으면 422. **경고** = 200 응답의 `warnings`로 전달. 규칙 JSON의 각 항목에 `severity` 필드를 둔다. **[제안]**

| 규칙 | 값 | 수준 | 근거 |
|---|---|---|---|
| 본문 길이 | 1~1,000자. 강조 제목·보조문구·부가정보를 합치고 변수는 예시값으로 치환한 길이 | 오류 | Solapi API 문서 |
| 부가정보 | 1~500자, 변수 불가 | 오류 | 시안, 네이버 클라우드 문서 |
| 변수 개수 | 최대 30개 (공식 가이드 40, NCP 30 → 엄격한 값) | 오류 | 공식 가이드, NCP |
| 변수 형식 | `#{이름}`, 빈 이름 불가 | 오류 | 공식 가이드 |
| 변수 예시값 | 모든 변수에 비어 있지 않은 예시값 필수 (LLM이 생성하므로 누락은 재생성 대상) | 오류 | 공식 가이드 |
| 본문 | 변수만으로 구성 불가 | 오류 | 공식 가이드 |
| 강조 제목 | 1~50자, 변수 허용 | 오류 | 시안 (공식 수치 미확인) |
| 강조 보조문구 | 1~50자, **변수 불가** | 오류 | NCP 문서 (시안은 허용 → 수정) |
| 템플릿 이름 | 1~40자 | 오류 | 시안 |
| 템플릿 코드 | `^[A-Za-z0-9_]{1,30}$` | 오류 | 시안 |
| 카테고리 | 시안의 7개 코드 중 하나 | 오류 | 시안 |
| 메시지 유형 | `BA`, `EX`만 생성 (`AD`, `MI`는 채널 추가 버튼이 붙는 유형이라 버튼 제외 범위와 함께 제외) | 오류 | 사용자 결정(버튼 제외)에서 도출 **[제안]** |
| 금지 문구(명백한 광고) | "지금 구매", "앱 설치", "특가", "(광고)" 등 짧은 목록 | 오류 | 심사 가이드 발송 불가 예시 |
| 주의 단어 | 할인·이벤트·쿠폰·혜택 등 단어 단위 | 경고 | 시안 (정보성 문맥에서도 쓰일 수 있어 오류로 두지 않음) |
| 보안 템플릿 | 보안 템플릿인데 본문에 "인증"이 없음 | 경고 | 시안 |

빌더는 구현 시 이 표를 JSON으로 옮기고, 시안의 `validate()`와 다른 부분(1,000자 계산 방식, 보조문구 변수, 변수 개수, 금지 표현 수준)을 표 기준으로 맞춘다.

### 6.2 API

`POST /api/templates/generate`

요청
```json
{ "prompt": "주문 관련 메시지 세팅해줘", "channel": "@mystore" }
```
- `prompt`: 필수, 1~500자 **[제안]**
- `channel`: 폼에서 사용자가 선택한 값. 생성 대상이 아니며 응답에 그대로 쓰지 않는다(채널은 사용자가 고른다 **[제안]**). 채널명을 본문에 넣을 때만 참고.

응답 200
```json
{
  "draft": {
    "category": "002001",
    "name": "주문 완료 안내",
    "code": "ORDER_COMPLETE_01",
    "msgType": "BA | EX",
    "emph": "NONE | TEXT",
    "title": "", "sub": "",
    "content": "#{고객명}님, ...",
    "extra": "",
    "security": false,
    "samples": { "고객명": "홍길동" }
  },
  "warnings": ["..."],
  "attempts": 1
}
```
- 필드 이름과 값은 시안의 `state` 객체와 동일하게 맞춘다(프론트에서 그대로 대입). `buttons`는 포함하지 않는다.
- `emph`는 `IMAGE`를 생성하지 않는다.
- `warnings`: 남은 **경고 수준** 항목(예: 주의 단어 포함). **오류 수준** 위반이 남으면 200을 주지 않고 422로 응답한다 **[제안]**.

응답 422 (생성 불가)
```json
{
  "reason": "AD_CONTENT | RULE_VIOLATION | UNCLEAR",
  "message": "사용자에게 보여줄 문장",
  "draft": { },
  "errors": ["본문이 1,020자입니다 (최대 1,000자)"],
  "warnings": []
}
```
- `draft`, `errors`, `warnings`는 `RULE_VIOLATION`일 때만 채운다. `draft`는 마지막 생성 결과다. **[사용자 결정: 위반 결과를 표시하고 사용자가 채울지 선택]**
- `AD_CONTENT`: 요청 자체가 광고성("할인 쿠폰 홍보 보내줘")일 때. 알림톡으로 보낼 수 없고 브랜드 메시지가 필요하다고 안내 **[제안]**
- `RULE_VIOLATION`: 재시도 후에도 오류 수준 위반이 남음
- `UNCLEAR`: 어떤 템플릿인지 판단 불가("세팅해줘"만 입력)

응답 502/504: Claude API 오류·타임아웃. 메시지는 일반 문구로, 내부 오류·키 정보는 노출하지 않는다.

### 6.3 LLM 호출 **[제안]**
- 모델 `claude-opus-5-5`, 단일 Messages API 호출(에이전트·도구 루프 아님).
- 구조화 출력(`output_config.format`, JSON 스키마)으로 6.2의 `draft` + `refusal`(`reason`, `message`, 생성 불가 시) 형태를 받는다.
- 시스템 프롬프트: `alimtalk-review-guide.md` 전문 + `alimtalk-rules.json` 수치 요약 + 카테고리 목록. 요청마다 바뀌지 않으므로 프롬프트 캐싱 적용.
- 사용자 메시지: 자연어 요청 + 채널명.
- thinking은 이 모델에서 끌 수 없음. effort는 `medium`(모델 기본값)으로 시작, 품질·응답 시간을 보고 조정.
- 거부(`stop_reason: refusal`) 처리 및 SDK 기본 재시도(429/5xx) 사용.
- 타임아웃 **[제안]**: Claude 호출 1회당 60초, 사용자 요청 전체 예산 120초. 다음 재시도 전 남은 예산이 60초 미만이면 재시도하지 않고 마지막 결과로 판정한다(오류가 남으면 422, 호출 자체가 실패했으면 504). 프론트 fetch 타임아웃은 130초, 로딩 중 "최대 2분 정도 걸릴 수 있습니다" 안내.
- Java SDK의 정확한 클래스·메서드 이름은 구현 시 공식 SDK 문서로 확인한다.

### 6.4 규칙 점검과 재생성 **[제안]**
- `RuleValidator`는 `draft`를 받아 `errors[]`, `warnings[]`를 반환한다. 시안의 `validate()` 로직을 Java로 옮기되 6.1.1 기준으로 수정한다.
- LLM은 글자 수를 정확히 세지 못하므로, 프롬프트에는 실제 제한보다 여유 있는 목표치를 준다(예: 합산 본문 1,000자 → "700자 이내"). 실제 판정은 코드가 정확한 제한값으로 한다. **[제안]**
- 오류가 있으면 이전 결과와 오류 목록을 구체적인 수치와 함께("현재 1,050자, 50자 이상 줄일 것") 붙여 재요청한다. **최대 2회 재시도(총 3회 호출)**. 그래도 오류면 422 `RULE_VIOLATION`(마지막 `draft` 포함).
- 금지 표현은 단순 포함 검사다. 명백한 광고 문구는 오류, 문맥에 따라 정보성일 수 있는 단어는 경고로 둔다(6.1.1). 정보성 여부 같은 판단은 LLM 지침에 맡기고 코드로는 검사하지 않는다.

### 6.5 화면 변경 (`alimtalk-template.html` → `static/index.html`)
- 상단에 자연어 입력 카드 추가: 텍스트 입력 + [생성] 버튼, 생성 중 로딩 표시(버튼 비활성화), 오류·경고 메시지 표시 영역.
- 422 `RULE_VIOLATION` 시 **[사용자 결정]**: 오류 목록을 표시하고 [그래도 폼에 채우기] [다시 생성] 버튼을 보여 준다. [그래도 폼에 채우기]는 아래 성공 시와 같은 방식으로 `draft`를 채우되, 오류 목록은 화면에 계속 남긴다. 그 외 422(`AD_CONTENT`, `UNCLEAR`)와 502/504는 메시지만 표시한다.
- 생성 성공 시: 기존 폼 값을 `draft`로 덮어쓴다. 사용자가 이미 입력한 내용이 있으면 덮어쓰기 전 확인 창을 띄운다 **[제안]**. 이후 `fillForm()` + `update()` 호출.
- 제거: "검수 요청 데이터 생성" 버튼과 검증 결과·페이로드 영역 **[사용자 결정]**.
- 수작업 기능 유지 **[사용자 결정, 2026-11-12 변경]**: 카카오가 제공하는 메시지 유형(기본형·부가정보형·채널추가형·복합형)과 강조 유형(선택 안 함·강조 표기형·이미지형·아이템리스트형), 버튼 섹션은 화면에서 모두 직접 설정할 수 있어야 한다. 자동 작성은 기본형·부가정보형 / 선택 안 함·강조 표기형만 채우며, 자연어 입력 카드에 이 범위를 안내 문구로 표시한다. 자동 작성 결과를 폼에 채울 때 버튼은 비운다.
- 유지: "예시로 초기화" 버튼 **[제안]**.
- 유지: 입력 칸별 글자 수 카운터와 초과 표시(사용자가 직접 수정할 때 필요), 미리보기, localStorage 임시 저장.
- 프론트 규칙 적용 범위 **[제안]**: 전체 검증은 하지 않고 카운터 제한값만 맞춘다. 값은 중복 정의하지 않고 `GET /api/rules`(규칙 JSON을 그대로 반환)로 받아 쓴다. (메시지 유형·강조 유형 선택지는 줄이지 않는다.)
- 상단 "로컬 Dry-run 모드" 표시는 "자동 작성 모드" 등으로 바꾸거나 제거 — 빌더 재량.
- 채널 목록은 시안의 예시 3개를 그대로 둔다.

### 6.6 설정·보안
- `application.yml`에는 키 없이 모델명·타임아웃·재시도 횟수만 둔다. 키는 `ANTHROPIC_API_KEY` 환경변수.
- 로그에 프롬프트 원문은 남겨도 되나 API 키·응답 헤더는 남기지 않는다.
- 인증이 없으므로 로컬/내부망 실행 전제. 외부 공개는 이번 범위 아님.

### 6.7 테스트
- `RuleValidator` 단위 테스트: 규칙표의 각 항목별 통과/위반 사례.
- `TemplateGenerator`: Claude 클라이언트를 목(mock)으로 대체해 재생성 루프(1회 성공, 재시도 후 성공, 최종 실패), 거부·타임아웃 처리 검증.
- 컨트롤러 테스트: 요청 검증(빈 prompt, 500자 초과), 200/422/502 응답 형태.
- 실제 Claude API 호출 테스트는 기본 빌드에서 제외하고, 키가 있을 때만 수동 실행하는 별도 태스크로 둔다(비용 발생).
